부록 A1 · 꼬리 질문 대비 ①

설계 선택에 대한 질문

왜 SQLite 인가?

파일 하나 · 서버 없음 · 파이썬에 내장이라 평가자가 설치 없이 바로 실행할 수 있어서. 대신 FK 기본 OFF · 느슨한 타입 · DATE 없음을 PRAGMA 와 CHECK 로 보완했습니다.

상태를 별도 테이블로 안 뺀 이유?

값이 3개로 고정되고 거의 바뀌지 않아 CHECK IN (...) 으로 충분합니다. 상태가 늘거나 상태별 설명이 필요해지면 member_status 테이블로 분리합니다.

리뷰 PK 를 (member_id, movie_id) 로 하면?

가능합니다. 다만 다른 테이블이 리뷰를 가리킬 때(예: 좋아요) 두 컬럼을 들고 다녀야 해서, 번호 PK + UNIQUE(member_id, movie_id) 로 했습니다.

A1

질문이 나왔을 때만 펼칩니다. SQLite 의 한계를 숨기지 않고 '이렇게 보완했다'로 답하는 것이 포인트입니다: FK → PRAGMA(모든 파일 첫 줄 + run_all), 타입 → CHECK, DATE → ISO 문자열 + date() 검사. UNIQUE(member_id, movie_id) 가 만든 자동 인덱스 sqlite_autoindex_review_1 이 B05 실행 계획의 member_id 탐색에 쓰이고, 2-4 의 '앞 컬럼 규칙' 설명의 근거가 됩니다.

SQL 세부에 대한 질문

Q14 를 윈도 함수로 풀면?

RANK() OVER (PARTITION BY genre_id ORDER BY avg_rating DESC) = 1 인 행. 동점도 같은 순위라 결과는 같습니다. 과제 범주(서브쿼리)에 맞춰 상관 서브쿼리를 썼습니다.

CASCADE 는 위험하지 않나?

맞습니다. 실수로 회원 하나를 지우면 리뷰가 조용히 사라집니다. 그래서 장르는 RESTRICT, 실무에선 회원도 소프트 삭제가 일반적입니다(Q16 은 동작 시연).

NOT IN 은 왜 피하나?

서브쿼리 결과에 NULL 이 하나라도 있으면 x NOT IN (…, NULL) 이 참이 될 수 없어 결과가 비어 버립니다. 없는 것 찾기는 NOT EXISTS 나 LEFT JOIN … IS NULL.
